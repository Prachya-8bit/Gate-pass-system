# คู่มือความหมาย Error — SYS Gate Pass

เอกสารนี้ไว้เปิดตอน debug เมื่อเจอ error จากระบบ ไม่ว่าจะเจอใน DevTools Network, ใน `automation/logs/sync.log` หรือบนหน้าจอผู้ใช้

ระบบนี้มี error 4 ชั้นที่ใช้ HTTP code คนละแบบ:

| ชั้น | ตัวอย่าง path | ยืนยันตัวตนด้วย | ไม่มีสิทธิ์ = code |
|---|---|---|---|
| หน้าเว็บ (middleware) | `/admin`, `/contractor` | JWT cookie `gp_token` | redirect หรือ **403** |
| App API | `/api/records`, `/api/users` | JWT cookie `gp_token` | **403** |
| Integration API (RPA) | `/api/integration/*` | header `x-api-key` | **401** |
| RPA script | `automation/epro-sync.mjs` | — | เขียนลง `sync.log` |

---

## 1. HTTP code ในระบบนี้หมายถึงอะไร

| Code | ในระบบนี้แปลว่า | เกิดที่ไหน |
|---|---|---|
| **200** | สำเร็จ — **แต่ไม่ได้แปลว่ามีอะไรเปลี่ยน** (ดูหัวข้อ 5 กับดักที่ 3) | ทุก route |
| **201** | สร้างข้อมูลใหม่สำเร็จ | `POST /api/records`, `POST /api/users` |
| **400** | ข้อมูลที่ส่งมาผิดรูป / ไม่ผ่าน validation / สถานะไม่ถูกต้องกับคำสั่ง | ทุก route |
| **401** | รหัสผ่าน login ผิด **หรือ** API key ของ RPA ผิด/ไม่ได้ส่ง | `auth/login`, `integration/*` |
| **403** | ไม่ได้ login **หรือ** login แล้วแต่ role ไม่ตรง | App API, middleware |
| **404** | ไม่พบ record/user ที่ระบุ **หรือ** ยิงไปที่ URL ที่ไม่มี endpoint | `users/[id]`, `records/[id]`, หรือ deploy ไม่ครบ |
| **409** | ข้อมูลชนกับที่มีอยู่ (credential ซ้ำ) | `POST /api/users` |
| **500** | **exception หลุดออกมาโดยไม่มีใครดัก** — ไม่ใช่ error ที่โค้ดตั้งใจคืน | ดูหัวข้อ 6 |
| **503** | server ยังไม่ได้ตั้ง `INTEGRATION_API_KEY` | `integration/*` |

> **สำคัญ:** 500 คือ error ที่โค้ด**ไม่ได้ตั้งใจ**คืน ทุก error ที่ตั้งใจจะมีข้อความไทยเสมอ ถ้าเจอ 500 แปลว่ามีอะไรพังในระดับที่โค้ดไม่ได้เตรียมรับมือ (เกือบทั้งหมดคือปัญหาฐานข้อมูล)

### Integration API (ที่ RPA เรียก)

| ข้อความ | Code | Route | สาเหตุ / วิธีแก้ |
|---|---|---|---|
| `ระบบยังไม่ได้ตั้งค่า INTEGRATION_API_KEY` | **503** | `integration/*` | ฝั่ง **server** ไม่มี env var นี้ — ตั้งใน Vercel dashboard |
| `ไม่มีสิทธิ์เข้าถึง` | **401** | `integration/*` | ฝั่ง **client** ส่ง `x-api-key` ผิดหรือไม่ได้ส่ง — ค่าใน `automation/.env` ต้องตรงกับที่ตั้งใน Vercel |
| `ต้องระบุ runId` | 400 | `claim`, `vehicle-claim` | — |
| `ต้องระบุ runId, batchKey, result` | 400 | `report`, `vehicle-report` | — |
| `ระบบฐานข้อมูลไม่พร้อมใช้งาน กรุณาลองใหม่` | **503** | `claim`, `vehicle-claim`, `vehicle-report` | transaction ล้ม (เกือบทั้งหมดคือ Neon cold start → `P2028`) — **retry ได้** RPA จะข้ามรอบแล้วเอาต่อรอบหน้าเอง ดูสาเหตุจริงใน Vercel Runtime Logs (`claim transaction failed` / `vehicle-claim transaction failed`) |

> **endpoint ของรถแยกจากของคนงาน** — `vehicle-claim`/`vehicle-report` เป็นคู่ใหม่ ไม่ได้เพิ่ม `formType` เข้า route เดิม เพราะ RPA บนเครื่องโรงงาน deploy แยกจาก Vercel ถ้าแก้ route เดิมแล้ว RPA เก่ายิงมา ผลที่เป็นไปได้คือ **200 พร้อม payload ผิดแบบเงียบ** ส่วนการแยก endpoint ทำให้ผลที่แย่ที่สุดเป็นแค่ **404** ที่ grep เจอในครั้งเดียว
>
> RPA ฝั่งรถจัดการ non-OK ต่างจากฝั่งคนงานเล็กน้อย: **404 = Vercel ยังไม่ได้ deploy → ข้ามเงียบ exit 0**
| `รูปแบบวันที่ต้องเป็น YYYY-MM-DD` | 400 | `GET /api/integration/records` | query `from` / `to` ผิดรูป |

> **แยก 401 กับ 503 ให้ออก:** 401 = กุญแจผิด (แก้ที่ฝั่ง RPA), 503 = ปัญหาฝั่ง server
>
> **⚠️ 503 มี 2 ความหมาย — ต้องอ่านข้อความประกอบ:**
> - `ระบบยังไม่ได้ตั้งค่า INTEGRATION_API_KEY` = ลืมตั้ง env var → แก้ที่ Vercel
> - `ระบบฐานข้อมูลไม่พร้อมใช้งาน กรุณาลองใหม่` = DB ไม่พร้อมชั่วคราว → **ไม่ต้องแก้อะไร** rerun เอง

| ข้อความ | หมายถึง | ต้องทำอะไร |
|---|---|---|
| `ไม่มีคำขอนำรถเข้าที่ต้องส่ง — จบการทำงาน` | ไม่มีใบสถานะ `CONFIRMED` รออยู่ | ปกติ |
| `ยังไม่มี endpoint vehicle-claim บนเซิร์ฟเวอร์ (HTTP 404) — ข้ามการส่งรถรอบนี้` | Vercel ยังไม่ได้ deploy โค้ดที่มี endpoint นี้ | ปกติระหว่างรอ deploy จบด้วย exit 0 ไม่กระทบ sync คนงาน |
| `เวลาเริ่มเหลือ N นาที (น้อยกว่า 60 นาที) epro จะไม่รับคำขอนี้` | **pre-flight ตัดทิ้งก่อนส่ง** เพราะ EPRO บังคับ 1 ชม.และ retry ยิ่งแย่เพราะเวลาเดินหน้า | รายงาน `permanent` → โผล่แถบเตือนแดง ต้องให้ผู้รับเหมายื่นใบใหม่ |
| `epro validation ไม่ผ่าน: <ข้อความ dialog>` | EPRO เด้ง alert หลังกด Save = **ไม่ได้บันทึก** | ถ้าไม่ดักไว้จะรายงาน `ok` แล้วแถวกลายเป็น "ส่งแล้ว" ทั้งที่ EPRO ว่าง — อ่านข้อความ dialog แล้วแก้ต้นเหตุ |
| `vehicle form selector not found — เปิดหน้าฟอร์มรถยนต์ไม่ได้` | เปิด `FrmOperation.aspx` แล้วไม่เจอ control ที่คาด | EPRO อาจเปลี่ยนหน้า → เก็บ selector ใหม่ (จัดเป็น `permanent` ไม่ retry) |
| `ไม่ทราบผล: <msg>` | พัง **หลัง** กด Save ผลไม่แน่นอน | → `ต้องตรวจสอบ` ต้องเปิด EPRO เช็คว่าเข้าจริงไหม **ห้ามเดา** |
| `ล้มเหลว (ถาวร/ลองใหม่ได้): <msg>` | พัง **ก่อน** กด Save = ไม่มีอะไรถูกบันทึก | `ลองใหม่ได้` จะถูกหยิบไปส่งอีกเอง · `ถาวร` ต้องมีคนแก้ |

> **แยกด้วย "กด Save ไปแล้วหรือยัง" ไม่ใช่ข้อความ error** — พังหลัง Save ต้องเป็น `unknown` เท่านั้น **ห้ามเป็น `failed`** เพราะ `failed` retry ได้ = เสี่ยงส่งซ้ำเข้า EPRO ซึ่งลบไม่ได้

## 4. สถานะของ record (`SyncStatus`)

จาก [lib/sync.ts](../lib/sync.ts) และ [prisma/schema.prisma](../prisma/schema.prisma)

| สถานะ | ป้ายไทย | ความหมาย |
|---|---|---|
| `PENDING` | รอยืนยัน | contractor เพิ่งกรอกเข้ามา admin ยังไม่ได้ตรวจ |
| `CONFIRMED` | ยืนยันแล้ว | admin ตรวจแล้ว **รอ RPA มาหยิบไปส่ง** |
| `SYNCING` | กำลังส่ง | RPA จองไว้แล้ว กำลังกรอกลง epro |
| `SYNCED` | ส่งแล้ว | เข้า epro เรียบร้อย |
| `FAILED` | ไม่สำเร็จ | ส่งไม่ผ่าน — จะถูกหยิบไปลองใหม่ถ้ายังไม่ครบ 3 ครั้ง |
| `NEEDS_REVIEW` | ต้องตรวจสอบ | **ไม่รู้ผล** ต้องมีคนไปเช็คใน epro เองว่าเข้าไปหรือยัง |
| `CANCELLED` | ยกเลิก | ถูกยกเลิก ไม่ส่ง |

เส้นทางปกติ: `PENDING` → `CONFIRMED` → `SYNCING` → `SYNCED`

ค่าคงที่ที่คุมพฤติกรรม ([lib/sync.ts](../lib/sync.ts)):

| ค่า | ปัจจุบัน | ผล |
|---|---|---|
| `MAX_ATTEMPTS` | 3 | ลองส่งได้ 3 ครั้ง เกินแล้วไม่หยิบไปลองอีก |
| `RETRY_BACKOFF_MS` | 5 นาที | `FAILED` ต้องรอ 5 นาทีก่อนถูกหยิบใหม่ |
| `CLAIM_TIMEOUT_MS` | 30 นาที | `SYNCING` ที่ค้างเกิน 30 นาที จะถูก reaper เปลี่ยนเป็น `NEEDS_REVIEW` |

## 5. กับดักที่ทำให้ debug ผิดทาง

**1. ข้อความ `ไม่มีสิทธิ์เข้าถึง` ใช้ทั้ง 403 และ 401**
ข้อความเดียวกันเป๊ะ แต่คนละสาเหตุ — **ต้องดู HTTP code ประกอบเสมอ**
- **403** = ปัญหา session ของคน (cookie หมดอายุ / role ไม่ตรง)
- **401** = ปัญหา API key ของเครื่อง (RPA คุยกับ server)

**2. App API คืน 403 ทั้งกรณี "ไม่ได้ login" และ "role ผิด"**
ไม่ได้แยก 401 ออกมา ดังนั้น 403 อย่างเดียวยังบอกไม่ได้ว่าเพราะ cookie หมดอายุหรือใช้บัญชีผิด role
และ `POST /api/records` ต้องเป็น **contractor** เท่านั้น — **admin ยิงเองจะได้ 403** ซึ่งดูขัดความรู้สึกแต่เป็นพฤติกรรมที่ตั้งใจ

**3. HTTP 200 ไม่ได้แปลว่ามีข้อมูลเปลี่ยน**
- `POST /api/integration/report` คืน `{"acknowledged": true}` **แม้จะไม่ตรงกับ record ใดเลย** (กรณี run เก่าที่ถูกแทนที่ไปแล้ว) — ตั้งใจให้เงียบ ไม่ถือเป็น error
- `POST /api/integration/claim` คืน `{"workOrder": null}` เมื่อไม่มีงาน — เป็น 200 ปกติ ไม่ใช่ error
- `POST /api/records/confirm` คืน `{"count": 0}` ถ้าไม่มี record ไหนอยู่สถานะ `PENDING`

ถ้าจะเช็คว่า sync ทำงานจริงไหม **ให้ดู `syncStatus` ในฐานข้อมูลหรือ `SyncLog` ไม่ใช่ดูแค่ HTTP code**

## 6. Playbook: `claim ล้มเหลว HTTP <code>`

นี่คือ error ที่เจอบ่อยที่สุดใน `sync.log` และทำให้ sync ทั้งรอบไม่ทำงาน

### HTTP 503 `ระบบฐานข้อมูลไม่พร้อมใช้งาน`

**นี่คือกรณีที่เคยเป็น HTTP 500 ดิบ — แก้แล้ว** (เดิม `claim` ครอบทุกอย่างใน `prisma.$transaction` โดยไม่มี `try`/`catch` และไม่ตั้ง `timeout` error จากฐานข้อมูลจึงกลายเป็น 500 ที่ไม่มีข้อความ และ RPA `exit 1` ทิ้งงานทั้งรอบ)

ตอนนี้ [app/api/integration/claim/route.ts](../app/api/integration/claim/route.ts) ตั้ง `{ timeout: 20_000, maxWait: 10_000 }` และดัก exception คืน 503 พร้อมข้อความไทย ส่วน RPA แยก **5xx = ข้ามรอบ (exit 0)** ออกจาก **4xx = config ผิด (exit 1)**

**ผลคือ:** DB สะดุดชั่วคราวกลายเป็นความล่าช้า 15 นาที ไม่ใช่การทิ้งงานทั้งรอบ **ไม่ต้องทำอะไร** ถ้าเจอนานๆ ครั้ง

**ถ้าเจอถี่** ให้เปิด Vercel → Runtime Logs หา `claim transaction failed` แล้วดูสาเหตุจริง:
1. **Prisma interactive transaction timeout** — `P2028` / `Transaction already closed` (Neon cold start กินเวลาเกิน)
2. **Neon connection / pool exhaustion** บน Vercel serverless — เช็คว่า `DATABASE_URL` เป็น **pooled** connection

**ข้อสังเกตที่ใช้ตั้งสมมติฐานได้:** เทียบเวลาในรอบที่พังกับรอบที่ผ่าน — รอบที่พังใช้เวลาเท่าตัวคือสัญญาณของ timeout

```
18:00:01 → 18:00:12   claim ล้มเหลว HTTP 503 — ข้ามรอบนี้   (12 วินาที)
18:15:01 → 18:15:07   ไม่มีใบงานที่ต้องส่ง                  (6 วินาที)
```

### HTTP 500

เหลือเฉพาะกรณีที่**ไม่มีใครดัก** — ไม่ใช่ปัญหาสิทธิ์ (401/503) ไม่ใช่ payload ผิด (400) และไม่ใช่ transaction ของ claim (503 แล้ว) เช่น `ensureCompanyExists()` เจอ unique violation ตอนสองคนยื่นชื่อบริษัทใหม่ชื่อเดียวกันพร้อมกัน ให้ดู Vercel Runtime Logs

### HTTP 404

**ไม่ใช่ error ของแอป** — แปลว่ายิงไปที่ URL ที่ไม่มี endpoint อยู่

สาเหตุที่เป็นไปได้:
- `GATEPASS_URL` ใน `automation/.env` ผิด
- ยังไม่ได้ deploy โค้ดที่มี `/api/integration/claim` ขึ้น production

### HTTP 401 / 503

ดูตารางหัวข้อ 2 — 401 แก้ที่ `automation/.env`, 503 แก้ที่ Vercel env vars
